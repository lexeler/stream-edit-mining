# stream-glue

Склейка кусков одного твич-стрима в единый файл и перенос монтажного листа
из Premiere на этот файл.

Задача, под которую сделано: качалка режет один непрерывный эфир на несколько
mp4, иногда с перехлёстом в пару секунд. Проект Premiere при этом ссылается на
каждый кусок отдельно. Нужен **один ролик и один плоский список таймкодов** к нему.

## Быстрый старт

```bash
python3 glue.py   <папка>                      # -> full_video.mp4 + offsets.json
python3 verify.py <папка>                      # проверка A/V синхронности
python3 remap.py  <папка> <проект.prproj>      # -> timecodes.txt + timecodes.json
```

Зависимости: `ffmpeg`, `ffprobe`, `numpy`.

## Как работает склейка

1. **Порядок** — по метке времени в имени файла (`..._2026-07-30 15-25-42_720p_...`).
2. **Перехлёсты** — нормированная взаимная корреляция звука между хвостом одного
   куска и началом следующего, через БПФ, по всем возможным величинам наложения.
   Порог `NCC >= 0.75`, и этого **мало** — найденный перехлёст обязательно
   подтверждается на 5 независимых окнах внутри предполагаемого наложения
   (`confirm_overlap`). Если хоть одно окно даёт меньше `0.80` — перехлёст
   отклоняется. См. «Ложный перехлёст» ниже: без этой проверки алгоритм
   вырезал 20 секунд живого материала.
3. **Резы на ключевые кадры.** Найденную величину перехлёста сажаем на ближайший
   ключевой кадр. У твич-качалки они каждые 2 с, промах выходит 5–15 мс, то есть
   меньше кадра.
4. **Склейка** — `ffmpeg concat` с `-c copy`. Ни видео, ни звук не проходят через
   кодировщик, биты переписываются в новый контейнер как есть.
5. **Замер смещений.** Где каждый кусок фактически оказался в результате —
   **измеряется** по звуку, а не вычисляется. Это принципиально: предсказание по
   длительностям контейнеров врёт примерно на 12 мс.

## Почему стрим-копирование, а не перекодирование

Резы попадают на ключевые кадры, поэтому перекодирование не нужно. Выигрыш:
качество не теряется вообще, склейка занимает минуты вместо часа.

## Проверка

`verify.py` меряет одно и то же событие двумя независимыми способами:

```
источник в момент s виден в результате на (t + La)   по звуку
источник в момент s виден в результате на (t - Lv)   по кадрам
рассинхрон = La + Lv                    <- знаки противоположны по построению
```

Обязателен **контрольный замер вдали от швов**: там результат обязан быть нулевым.
Если контроль не нулевой — врёт метод, а не склейка, и цифрам на швах верить нельзя.

`remap.py` проверяет иначе: берёт кадр из склейки по новому таймкоду и кадр из
исходника по старому и сравнивает попиксельно. Разница обязана быть 0.00.

## Пределы точности

| Что | Предел | Откуда |
|---|---|---|
| Положение видео | ±8,3 мс | половина кадра при 60 fps |
| Рез видео | ключевой кадр | GOP 2 с у твич-качалки |
| Рез звука | 21,3 мс | AAC-кадр = 1024 сэмпла при 48 кГц |
| Положение звука | доли мс | корреляция на 16 кГц |

Всё, что меньше 8,3 мс, измерить нельзя — это ноль.

## Известный дефект: рассинхрон на швах

В исходниках звук стартует раньше видео, и **на разную величину**: замеры на
слоте 1 дали 5, 5, 11, 5 и 21 мс. Пока сдвиг одинаковый, он безобиден — он есть
во всём ролике целиком. На шве, где сдвиг меняется, разница и вылезает.

Результат на слоте 1: три шва в пределах погрешности, четвёртый **+20 мс**
(1,2 кадра) — там кусок с нестандартными 21 мс. Порог заметности у человека
около 100 мс, так что на просмотре это не видно.

Если понадобится добить до нуля: перед склейкой выровнять все куски по
`start_time` аудио через `-itsoffset`, подавая файл на вход дважды —
видео с первого входа, звук со второго. Перекодирования не требует.
На практике проверено не было.

## Ложный перехлёст — как чуть не потеряли 20 секунд

На слоте 3 первая версия алгоритма (порог `0.55`, без подтверждения) нашла на
стыке 3→4 «перехлёст» **19,221 с при NCC 0.55** и вырезала его. Материала на
20 секунд стало меньше, и заметить это по итоговым цифрам было нельзя: пересчёт
таймкодов сошёлся с проектом до 0,0 мс, кадровая сверка прошла.

Два признака, по которым ложное срабатывание всё-таки видно:

- **NCC у самого порога.** Настоящие перехлёсты давали 0,94–0,98, этот 0,55.
- **Большой промах при посадке на ключевой кадр.** У настоящих 5–12 мс,
  здесь 796 мс (47,7 кадра). Настоящий перехлёст у этой качалки всегда
  примерно равен одному интервалу между ключевыми кадрами (~2 с).

Лечение: порог поднят до `0.75` плюс обязательное подтверждение на независимых
окнах. После этого стык 3→4 корректно опознаётся как «перехлёста нет».

**Мораль: одной корреляции недостаточно, нужна независимая перепроверка.**
И проверять надо ДО удаления исходников — иначе чинить будет нечем.

## Тупик с перекодированием звука

Была попытка вылечить рассинхрон, подрезав в каждом куске звук ровно под длину
видео. **Стало хуже.** Перекодирование AAC добавляет задержку кодировщика ровно
в 1024 сэмпла (21,3 мс), и контрольная точка из нулевой стала +21,3 мс,
а швы уехали до 170 мс.

**Вывод: звук не перекодировать.** Только стрим-копирование.

## Про монтажный лист

Проект Premiere для такого материала оказался плоским списком «оставить»:
одна видеодорожка, одна звуковая, клипы стык в стык, без перестановок,
без изменения скорости, без переходов. То есть он честно переводится
в текстовый список отрезков.

`remap.py` берёт только видеодорожку — аудиоклипы дублируют её один в один
(проверено: 0 различий по Start, End, InPoint, OutPoint на всех 535 парах).

**Что теряется:** эффекты. В разобранном проекте нашлось 6 «Быстрых размытий»
и 6 «Масок» — в список таймкодов они не попадают.
